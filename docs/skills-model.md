# Модель компетенций: граф навыков, подтверждения, грейд

Статус: черновик 6 октября 2026 (по плану команды §3). Числовые параметры (веса, полураспады,
пороги профилей) живут в `backend/app/skills/<spec>/graph.yaml` и `grade_profiles.yaml`;
документ описывает смысл и формулы, цифры при расхождении берутся из YAML.

## 1. Теоретическая основа и что в ней наше

**Теоретическая основа: «Квантовая модель компетенций» Константина Кичинского (2023, открытая
публикация, spectralthinking.org). Графы, шаблоны заданий, формулы и применение к подбору
персонала — разработка команды.**

Из модели мы берём идеи, а не текст и не иллюстрации: все схемы в документации и интерфейсе
нарисованы заново (граф точками и рёбрами), названия и описания узлов — наши. Короткая
аттрибуция повторяется в `02-testing.md` §1 и на одном слайде презентации. Автору модели
отправлено уведомление о применении на хакатоне (черновик — `drafts/letter-to-author.md`).

| Идея из модели | Как применяем в «Орбите» | Что добавили сами |
|---|---|---|
| Карта предметной области делится на три слоя: глубинные основы, рабочая база и контекст применения | Три слоя узлов у каждой специализации: **D** (глубина), **B** (база), **C** (контекст) | Конкретные графы для бэкенда, фронтенда и данных (preview) |
| Навыки роли сворачиваются в 10–15 композитных блоков | 13 узлов на специализацию | Названия, описания узлов и критерии их подтверждения |
| Уровень специалиста определяется связностью подтверждённых навыков, а не их числом | Квантовый уровень `Q = |A| − C(A)` по активным узлам (размер остовного леса) | Профили грейдов junior/middle/senior поверх Q; грейд выводится из теста, а не из самоописания |
| У навыка есть срок годности; неиспользуемое угасает, но восстанавливается усилием | Подтверждение с датой, весом и полураспадом; сила узла — noisy-OR; регулярные задания «реанимируют» узел | Формула силы, полураспады по источнику и слою, состояния «свежо / тускнеет / погасло» |
| Оценивать стоит свершения (что человек сделал), а не перечень обязанностей | Форма свершений кандидата; потребность работодателя описывается через задачи первых трёх месяцев; достижение ФСП — свершение с датой и верификацией | Персональные сценарные задания из свершений; маппинг дисциплин ФСП в узлы |
| Формы профиля I / T / П, «ходоки» и «хабы» | Бейдж формы в карточке кандидата, фильтр у работодателя; мосты между специализациями | Детерминированный расчёт формы по активным узлам |
| Покрытие карты командой, организационный взгляд | В MVP не реализуем; описано как развитие (`09-beyond-mvp.md`) | — |

## 2. Специализации и графы

Справочник хранится в YAML (`backend/app/skills/<spec>/graph.yaml`, поле `graph_version`) и сидом
загружается в таблицы `specialization`, `skill_node`, `skill_edge`, `grade_profile`. Новая
специализация = новый YAML плюс банк шаблонов. Отрасль (`industry`) — короткий справочник,
влияет только на отображение и фильтр; категория кандидата = специализация × грейд.

| Код | Специализация | Статус | Что есть |
|---|---|---|---|
| `be` | Бэкенд | `active` | граф 13 узлов + банк шаблонов + тест |
| `fe` | Фронтенд | `active` | граф 13 узлов + банк шаблонов + тест |
| `data` | Данные | `preview` | только граф; в опросе не предлагается, теста нет |
| `qa`, `devops` | Тестирование, DevOps | `preview` | только граф — чтобы разбирать такие вакансии при проверке жюри |

Preview-специализация не создаёт тупика «скоро»: кандидату она не предлагается, а категория
по ней возможна только через сид или служебный импорт (для синтетических кандидатов и пар жюри).

Рёбра вида `bridge` соединяют узлы разных графов: `be.B1`–`fe.C2` (контракт API),
`be.C1`–`fe.C1` (поставка), `be.B5`–`fe.B5` (безопасность), `be.C4`–`fe.C4` (команда).
Мосты нужны для форм T/П и для межспециализационных потребностей работодателя
(«бэкенд + фронтенд»): мостовой узел в подграфе потребности считается как обычный.

## 3. Подтверждения и сила узла

Единица данных — подтверждение `skill_confirmation(candidate_id, node_id, level, w0, source,
source_ref, confirmed_at, half_life_days)`. Узел кандидата не «есть или нет», а подтверждён
набором датированных свидетельств разной силы.

### 3.1. Источники и базовый вес `w0`

| Источник | Базовый вес `w0` | Уровень подтверждения |
|---|---|---|
| Тест (`test`) | балл узла ≥ 0.85 → 1.0; ≥ 0.7 → 0.85; ≥ 0.5 → 0.45; < 0.5 — подтверждения нет (балл остаётся в сессии) | уровень заданий сессии (L1/L2/L3) |
| Достижение ФСП (`fsp`) | победа 1.0; призёр 0.8; финалист 0.6; участие 0.35 | по маппингу дисциплины (раздел 6) |
| Регулярное задание (`regular`) | решение ≥ 0.7 → 0.6; подход ≥ 0.5 → 0.3 | уровень задания |
| Свершение из анкеты (`self`) | 0 — на силу не влияет; определяет, что проверять, и даёт контекст сценарных заданий | — |

### 3.2. Затухание

Полураспад подтверждения зависит от источника и слоя узла: `τ = τ_source × k_layer`.

| Параметр | Значение | Почему |
|---|---|---|
| `τ_test` | 240 дней | результат теста актуален примерно два квартала |
| `τ_fsp` | 365 дней | достижение верифицировано внешней стороной, затухает медленнее |
| `τ_regular` | 120 дней | короткое задание — свежий, но менее глубокий сигнал |
| `k_D` | 1.5 | фундаментальные знания забываются медленнее |
| `k_B` | 1.0 | базовая норма |
| `k_C` | 0.75 | инструменты контекста меняются быстро |

Вес подтверждения `e` в момент `t`: `w_e(t) = w0_e · 2^(−(t − t_e) / τ_e)` — через один
полураспад остаётся половина, через два — четверть.

### 3.3. Сила узла

Сила узла `v` на уровне `L` в момент `t` — noisy-OR по подтверждениям этого узла с уровнем
не ниже `L`:

```
S_v(L, t) = 1 − Π_e ( 1 − w0_e · 2^(−(t − t_e) / τ_e) ),   e ∈ подтверждения v, level_e ≥ L
```

Словами: каждое подтверждение — независимый «шанс», что навык действительно есть; узел силён
настолько, насколько маловероятно, что все свидетельства разом ошибочны. Несколько слабых
свидетельств усиливают друг друга, одно сильное почти насыщает узел, и ни одно не даёт больше 1.

Узел **активен на уровне L**, если `S_v(L, t) ≥ 0.5`. Следствия, которые показываем жюри:

- одно слабое подтверждение (0.45) узел не активирует;
- старый тест 0.45 плюс свежее регулярное задание 0.3: `1 − 0.55 · 0.7 = 0.615` — узел
  активен («память реанимирована усилием»);
- свежий сильный тест (1.0) в слое B держит узел активным ≈ 240 дней: через полураспад вес 0.5
  ещё на границе, дальше нужна поддержка.

### 3.4. Свежесть для интерфейса

`w_now = max_e (w0_e · decay_e)` — вес самого сильного на сегодня подтверждения узла.

| Состояние | `w_now` | Что видит кандидат |
|---|---|---|
| свежо | ≥ 0.8 | зелёный узел |
| тускнеет | 0.5–0.8 | жёлтый узел, подсказка «обновите подтверждение» |
| погасло | < 0.5 | серый узел: «подтверждение устарело — обновите регулярным заданием или тестом», кнопка на задание именно по этому узлу |

Реализация: чистые функции `app/modules/skills/strength.py` с юнит-тестами на примеры выше;
материализованный снимок `candidate_skill_state(candidate_id, node_id, active_level,
strength_by_level, w_now, freshest_at)` пересчитывается при каждом новом подтверждении
и ночной джобой `decay-recompute`.

## 4. Квантовый уровень Q и грейд

### 4.1. Уровень Q

`Q = |A| − C(A)`, где `A` — активные узлы кандидата (на уровне ≥ L1), `C(A)` — число компонент
связности подграфа, порождённого `A`. Это размер остовного леса: один узел → `Q = 0`; цепочка
из четырёх связанных → `Q = 3`; четыре узла в двух несвязанных парах → `Q = 2`. Разрозненные
навыки дают меньший уровень, чем те же навыки, связанные рёбрами графа. Q показывается обеим
сторонам («уровень по графу: 7 из 12») и входит в ранжирование как связность.

### 4.2. Профили грейдов

Грейд (категория из требований: присваивается только по опросу и тесту) считается через профиль
`grade_profile(spec, grade)`: целевой подграф `T`, уровень заданий и пороги. Берутся подтверждения
**текущей тестовой сессии** на `T` — затухание и достижения ФСП на ярлык грейда не влияют,
они меняют силу профиля и позицию в рейтинге.

| Грейд | Целевой подграф T (`be`; `fe` — те же коды) | Уровень заданий | Порог |
|---|---|---|---|
| junior | {B1, B2, B3, D1} | L1 | ≥ 3 из 4 активны и `Q_T ≥ 2` (узлы связаны) |
| middle | {B1, B2, B3, B4, D1, D4, C1} | L2 | ≥ 5 из 7 активны, `Q_T ≥ 4`, активен ≥ 1 узел вне слоя B |
| senior | {B1, B2, B3, B4, B5, D3, D4, C1, C2, C3} | L3 | ≥ 7 из 10 активны, `Q_T ≥ 6`, активны ≥ 1 узел D и ≥ 1 узел C («ходок») |

«Справился уверенно» — все узлы `T` активны и средний балл ≥ 0.85 → предлагается тест на грейд
выше. Не прошёл — ярлык не понижается: кандидат видит, каких узлов не хватило, и предложение
теста на грейд ниже; подтверждённые узлы сохраняются.

### 4.3. Демо-профили

Для жюри и стенда есть `grade_profile(mode = demo)`: связный подграф из `T` с теми же
структурными условиями, но меньше узлов, без вторых заданий и без персонального сценария
(3–5 заданий, 6–10 минут). Результат присваивает категорию с пометкой «в демо-режиме»,
подтверждения получают `w0 × 0.85`.

| Грейд | Демо-подграф (`be`) | Порог |
|---|---|---|
| junior | {B1, B2, D1} | ≥ 2 из 3 активны, `Q ≥ 1` |
| middle | {B1, B2, D1, C1} | ≥ 3 из 4, `Q ≥ 2`, ≥ 1 узел вне B |
| senior | {B1, B4, D4, C2, C3} | ≥ 4 из 5, `Q ≥ 3`, ≥ 1 узел D и ≥ 1 узел C |

Юнит-тест проверяет, что каждый демо-подграф связен по рёбрам своей специализации и проходим
при верных ответах.

### 4.4. Правила смены грейда

- после присвоения категории повторный тест доступен через `GRADE_COOLDOWN_DAYS` (90 дней;
  на стенде `DEMO_COOLDOWN_SECONDS=60`, чтобы жюри увидело повторный тест за минуты);
- в течение 48 часов после первичного теста — одна попытка на соседний грейд (вверх при
  «уверенно», вниз при «не прошёл») без ожидания;
- провал без категории: в окне 48 часов — одна попытка на грейд ниже; дальше повтор не раньше
  `RETRY_AFTER_DAYS=7` (на стенде `DEMO_RETRY_SECONDS=60`), задания заведомо новые, не более
  трёх провалов на специализацию за 90 дней;
- провал при наличии категории: категория не меняется, подтверждённые узлы остаются;
- `GET /tests/eligibility` возвращает состояние и дату следующей попытки — интерфейс строится
  только из этого ответа, тупика нет;
- история опросов и тестов (включая провальные и демо-сессии) — на странице «Категория и грейд».

Категория: код `be:middle`, отображение «ИТ · Бэкенд · Middle». На карточке — **подтверждённый
стек** (технологии из заданий, решённых верно) и отдельно «заявлено в анкете» с пометкой.

## 5. Формы профиля, ходок, хаб

Форма считается детерминированно по активным узлам:

| Форма / бейдж | Условие |
|---|---|
| точка | 1 активный узел |
| I | активные узлы только в своей специализации, охватывают ≥ 2 слоёв |
| T | I плюс ≥ 1 активный узел другой специализации через мост |
| П | T плюс в соседней специализации активны узлы ≥ 2 слоёв |
| ходок | активны узлы всех трёх слоёв своей специализации |
| хаб | активные мосты в ≥ 2 другие специализации (при двух специализациях в MVP недостижим, остаётся в коде и документации) |

Бейдж формы показывается в карточке кандидата и доступен как фильтр у работодателя.
Покрытие графа командой организации — только в «Развитии».

## 6. Достижения ФСП как подтверждения узлов

Запись `fsp_achievement(candidate_id, fsp_id, event_id, title, discipline, event_type, event_date,
result_tier, rank, percentile, is_team, raw)` превращается в подтверждения по статическому маппингу
`backend/app/skills/fsp_mapping.yaml`:

| Дисциплина / тип события | Узлы | Уровень |
|---|---|---|
| Алгоритмическое программирование (олимпиада) | D2 (1.0), D1 (0.6) | по перцентилю: топ-10 % → L3, топ-30 % → L2, иначе L1 |
| Хакатон, трек «бэкенд» | B1, B2, C1, C4 (вес по результату) | финалист/победитель → L2, участник → L1 |
| Хакатон, трек «фронтенд» | fe.B1, fe.B2, fe.C1, fe.C4 | то же |
| CTF / информационная безопасность | B5 (1.0), C3 (0.5) | призёр → L2, иначе L1 |
| Продуктовое программирование | C4, B1 | L1–L2 |
| Командное событие | дополнительно C4 × 0.5 | — |
| Участие без результата | только свежесть: `w0 = 0.2` на узлах трека | L1 |

`w0 = w_tier × w_node`, `τ = 365 × k_layer`. Структура данных о достижениях — наше предложение
реестру ФСП (участник, событие, результат, ссылка на протокол); реальный состав полей
запрашиваем у экспертов (`drafts/questions-to-fsp.md`) и фиксируем в `05-fsp-integration.md`.

## 7. Кандидат без истории ФСП

`fsp_id = null`, ФСП-подтверждений нет, компонент `fsp` в ранжировании равен 0. Формула подбора
аддитивна — ни штрафа, ни деления на ноль; карточка показывает «Достижения ФСП не привязаны;
профиль подтверждён тестом». В сиде не менее 40 % кандидатов без ФСП; отдельный тест валидации
проверяет, что такой кандидат при равном покрытии не выпадает из выдачи.

## 8. Кандидат без категории

Опрос и тест — обязательный путь к категории. Пока категории нет, профиль не ищется и
не попадает в подборку, приглашение невозможно (403 `candidate_not_categorized`); кабинет
показывает степпер «Путь до категории» с текущим шагом, а после провала — список недостающих
узлов и дату следующей попытки. Импортированные при проверке жюри резюме живут в отдельной
таблице и кандидатами не являются (подробнее — `03-matching.md`, `compliance.md`).
