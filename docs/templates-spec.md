# Спецификация шаблона задания (`task_template`)

Документ описывает формат YAML-шаблонов банка заданий «узел × уровень» (PLAN.md §4.1),
правила их написания и вычитки. Он адресован трём читателям: автору шаблона (человек или
агент-черновик), рецензенту (человек или агент по чек-листу §10) и коду
(`backend/app/modules/assessment/templates.py` — схема `TaskTemplate`, загрузчик и валидация).
Эталоны — восемь шаблонов в `backend/app/skills/{be,fe}/templates/`, написанные 6 октября.

## 1. Место шаблона в конвейере

```
шаблон (YAML, в репозитории)
   └─ variant_generate (LLM, t = 0.8) → вариант {statement, code?, options?, answer_key?, …}
        └─ variant_judge (LLM, t = 0) сверяет вариант с anchor_variant шаблона
             └─ пул вариантов (≥ 10 принятых на шаблон) → адаптивная сессия
                  └─ ответ кандидата: ключ (код) + answer_grade по rubric (LLM или эвристика)
```

Принцип: **сложность задаёт шаблон, уникальность — вариант, сопоставимость — судья.**
Шаблон не содержит «правильный ответ на экзамене» — он содержит *что проверяем*, *что нельзя
менять*, *на чём ловим* и *как судим*; конкретное условие кандидат видит только в варианте.
Открытость шаблонов в репозитории — открытость программы экзамена, а не ответов (§4.5 плана).

## 2. Расположение и именование

```
backend/app/skills/<spec>/templates/<NODE>/L<level>_<slug>.yaml
                   be     templates   D4     L2_composite_index.yaml
```

- `<spec>` — код специализации (`be`, `fe`, …), совпадает с каталогом `graph.yaml`;
- `<NODE>` — код узла без префикса специализации (`B1`, `D4`, `C2`);
- `L<level>` — уровень 1..3; `<slug>` — короткое английское имя в snake_case.
- `id` шаблона обязан совпадать с путём: `<spec>.<NODE>.L<level>.<slug>`
  (`be.D4.L2.composite_index`); `node` = `<spec>.<NODE>`. Загрузчик это проверяет.

Полный банк MVP: 2 специализации × 13 узлов × 3 уровня = 78 шаблонов (минимум — 65 без `fe` L3).

## 3. Поля шаблона

Все поля обязательны, если не отмечено иное. Неизвестные поля — ошибка загрузки
(защита от опечаток и «подсказок» вне схемы).

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `str` | `<spec>.<NODE>.L<level>.<slug>`; уникален в банке |
| `node` | `str` | узел графа `be.D4`; должен существовать в `graph.yaml` той же специализации |
| `level` | `1 \| 2 \| 3` | уровень задания (§5) |
| `kind` | enum | `mcq_reasoned`, `code_review`, `short_design`, `scenario_personal` (§4) |
| `title` | `str` (5–120) | короткое название для админки и отчётов; не показывается кандидату |
| `concept` | `str` | **что проверяем**: концепция одной-двумя фразами, в терминах узла (описание узла в `graph.yaml` — ориентир). Судья использует её для `same_concept` |
| `invariant` | `str` | **что должно сохраниться в любом варианте**: структура ситуации, число условий, наличие ловушки, формат ответа. Это главный контракт для генератора |
| `vary` | `str` | **что генератор меняет**: предметная область, имена, числа, порядок опций, стек в пределах `stack_tags` |
| `forbidden_changes` | `str` | **чего генератор не делает**: не подсказывать ответ в условии, не менять число условий/опций, не вводить материал другого уровня, не создавать вторую верную опцию |
| `trap` | `str` | **на чём ловим**: правдоподобная ошибка, которую должен содержать каждый вариант (судья проверяет `has_trap`); обычно одна-две неверные опции или «очевидное» неверное решение |
| `defect_class` | `str`, только `code_review` | класс дефекта в snake_case (§4.2); для остальных видов не задаётся |
| `stack_tags` | `list[str]` (1–8) | технологии задания строчными: `postgresql`, `react`, `http`; верно решённые задания формируют **подтверждённый стек** кандидата |
| `rubric` | `list` (2–6) | критерии судьи `{id, w, text}`; Σ `w` = 1 (§6) |
| `anchor_variant` | объект | эталонный вариант (§4): `statement`, `code?`, `options?`, `answer_key?`, `reference_answer`, `estimated_minutes` |
| `difficulty_anchor` | `{p_junior, p_middle, p_senior}` | ожидаемая доля верных ответов по грейдам, монотонна (§7) |
| `max_time_sec` | `int` (60–900) | серверный лимит на задание; `estimated_minutes × 60 ≤ max_time_sec` |
| `max_answer_chars` | `int`, по умолчанию 800 | лимит длины открытого ответа (обоснование / объяснение / проект) |
| `status` | `draft \| reviewed` | в пул уходят только `reviewed` (§9) |
| `author` | `str`, необяз. | кто написал: «эталон, 6 октября (W4)», «агент-черновик 7 октября» |
| `review` | `{by, at, notes}`, необяз. | кто и когда вычитал; заполняется при переводе в `reviewed` |

Комментарии YAML (`# …`) допустимы для пояснений рецензенту; в генератор и к кандидату
они не попадают.

### 3.1. Как писать `concept / invariant / vary / forbidden_changes / trap`

Эти пять полей — инструкция генератору и судье, а не текст для кандидата. Правила:

- `concept` отвечает на вопрос «что должен знать/уметь человек, чтобы решить *любой* вариант»;
  не пересказывает условие эталона.
- `invariant` перечисляет структурные элементы, которые обязаны быть в каждом варианте:
  «два условия равенства + сортировка + LIMIT», «ровно одна идемпотентная опция»,
  «в коде ровно один дефект». Если инвариант нарушен — судья обязан отклонить вариант.
- `vary` — то, что делает варианты непохожими (дедупликация Жаккаром > 0.6 отбрасывает
  перефразы): домен, сущности, числа, порядок опций.
- `forbidden_changes` закрывает типичные способы испортить задание: подсказка ответа
  терминами в условии, вторая верная опция, смена уровня, лишний дефект.
- `trap` описывает ловушку так, чтобы её можно было *узнать* в варианте: какая неверная
  опция/решение выглядит правдоподобно и почему.

Условие и опции пишутся по-русски; идентификаторы, код, SQL, HTTP — на английском.
Текст ТЗ хакатона и фрагменты книги Кичинского в шаблоны не копируются.

## 4. Виды заданий

Песочницы исполнения кода нет (осознанно, PLAN.md §10): все виды проверяются ключом и/или
судьёй по рубрике. Доля детерминированно проверяемого балла — константа
`DETERMINISTIC_SHARE` в `templates.py`.

| `kind` | Что видит кандидат | Что отвечает | Оценка |
|---|---|---|---|
| `mcq_reasoned` | условие + 4 опции (перемешаны) | одна опция + обоснование 1–2 предложения | опция по ключу **70 %**, обоснование судьёй по рубрике **30 %** |
| `code_review` | условие + фрагмент кода 15–40 строк с нумерацией | номер строки + объяснение (причина, исправление, проверка) | строка по ключу **50 %**, объяснение судьёй **50 %** |
| `short_design` | инженерная ситуация | открытый ответ до `max_answer_chars` (800) | судья по рубрике **100 %** |
| `scenario_personal` | условие, построенное из свершения кандидата | открытый ответ | судья по рубрике **100 %**; одно на сессию для middle+, заменяет обычное задание на узле со свершением |

### 4.1. `anchor_variant` по видам

| Поле | `mcq_reasoned` | `code_review` | `short_design` | `scenario_personal` |
|---|---|---|---|---|
| `statement` | условие + вопрос + «выберите один и обоснуйте» | симптом, контекст (модели, настройки), «строки пронумерованы с 1», что указать | ситуация + перечень того, что должен содержать ответ + лимит знаков | *пример* условия (реальное строится из свершения) |
| `code` | — (допустим короткий фрагмент в `statement`) | **обязателен**, 15–40 строк, ровно один дефект класса `defect_class` | — | — |
| `options` | **ровно 4**, ключи `A`–`D`, тексты не повторяются | — | — | — |
| `answer_key` | буква верной опции | `{line, accepted_lines}`: каноническая строка и строки, засчитываемые как верные | — | — |
| `reference_answer` | верная опция + почему неверны остальные | строка, механизм дефекта, исправление, проверка | образцовый ответ на все пункты условия | образцовый ответ |
| `estimated_minutes` | 1–3 | 2–4 | 3–7 | 4–8 |

Правила `mcq_reasoned`: ключ соответствует порядку опций в эталоне; при показе опции
перемешиваются, маппинг хранит сервер. Неверные опции должны быть *правдоподобны* для
человека без нужного знания; хотя бы одна из них — ловушка из `trap`. Нельзя делать опцию
«все вышеперечисленное» и опции-антонимы, выдающие ответ.

Правила `code_review`: дефект **один**, остальной код корректен и идиоматичен (иначе
кандидат укажет «тоже дефект» и будет прав); в комментариях и именах нет подсказок; класс
дефекта называется в условии (кандидат ищет *где* и объясняет *почему*, а не угадывает
класс). `accepted_lines` включает каноническую строку и строки, которые рецензент признаёт
верным указанием на тот же дефект (например, строка запроса без eager-load при N+1,
проявившемся в цикле). Код приводится с отступами, как в реальном проекте; без номеров
строк — их добавляет UI.

Рекомендуемые `defect_class` (snake_case, список открыт): `n_plus_one`, `race_condition`,
`sql_injection`, `resource_leak`, `missing_transaction`, `unsafe_get_side_effect`,
`unbounded_query`, `secret_in_code`, `broken_auth_check`; для фронтенда —
`stale_derived_state`, `stale_closure`, `missing_effect_cleanup`, `unstable_list_key`,
`unsafe_html`, `unmemoized_dependency`, `blocking_main_thread`.

Правила `short_design`: условие перечисляет, что должен содержать ответ (это и есть
рубрика «наоборот»), содержит конкретные числа и ограничения (размер данных, число клиентов,
кого нельзя обновить), даёт чужое утверждение или решение как объект оценки на L2–L3.
`reference_answer` — не «идеальный», а *достаточный* ответ на полный балл в пределах лимита
знаков; судья сравнивает с рубрикой, а не с текстом эталона (флаг `too_close_to_reference`
отмечает дословные совпадения).

## 5. Уровни L1–L3

| Уровень | Что проверяет | Как выглядит условие | Критерий «это точно L» |
|---|---|---|---|
| **L1** — применение по образцу | знание правила/механизма и умение узнать его в типовой ситуации | одна ситуация, один вопрос, одно верное действие; знакомые термины | junior с базовой подготовкой решает за 2–3 минуты; у ответа нет «зависит от…» |
| **L2** — анализ и проектирование с компромиссом | найти причину по симптому или спроектировать решение, назвав его цену | симптом + контекст, или задача с требованиями, которые конфликтуют (нагрузка vs целостность, совместимость vs скорость) | требует объяснить *почему* и назвать хотя бы один trade-off; есть правдоподобное неверное решение (trap) |
| **L3** — неочевидный случай в контексте, цена решения | увидеть скрытую несовместимость/риск, выбрать стратегию и обосновать её стоимость | ситуация с внешними ограничениями (чужие команды, legacy, деньги, сроки), чужое «очевидное» предложение, которое нужно оценить | middle в среднем не решает полностью; ответ содержит план с этапами и явную цену; «правильных» стратегий может быть две, рубрика оценивает обоснование |

Ориентиры `difficulty_anchor` по уровням: L1 ≈ `{0.55–0.65, 0.85, 0.95}`,
L2 ≈ `{0.3, 0.7–0.75, 0.9}`, L3 ≈ `{0.1, 0.4, 0.8}`. Профили грейдов используют уровень
заданий как уровень сессии: junior — L1, middle — L2, senior — L3 (PLAN.md §3.4).

Признаки неверно выбранного уровня: L1 с «назовите цену решения» (это L2); L2, решаемый
по одному правилу без анализа (это L1); L3 без внешнего контекста и без оценки стоимости
(это L2).

## 6. Правила рубрики

- 2–6 критериев; `id` — snake_case, уникален внутри шаблона; `w` ∈ (0, 1], Σ `w` = 1
  (допуск 1e-6).
- Критерий формулируется как **наблюдаемый признак ответа**, который судья отмечает
  `hit ∈ {0, 0.5, 1}` с цитатой-evidence: «объясняет окно между SELECT и INSERT», а не
  «понимает транзакции». Балл задания = Σ `w · hit` (для mcq/code_review — только доля судьи).
- Первый критерий — самый тяжёлый и соответствует `concept`; последний обычно про цену,
  проверку или отработку дистракторов.
- Для `mcq_reasoned` рубрика судит **обоснование**: «называет механизм», «отличает верную
  опцию от ловушки». Для `code_review` — объяснение: «механизм дефекта», «исправление»,
  «как проверить».
- Критерий не должен требовать дословной формулировки или конкретного инструмента, если
  есть равноценные (selectinload *или* joinedload *или* JOIN).
- Веса в сумме с детерминированной частью дают «порог активности» узла 0.7 (§4.3):
  шаблон не должен позволять набрать ≥ 0.7, угадав ключ и написав пустое обоснование.
  Для mcq это выполняется автоматически (0.7 × 1 + 0.3 × 0 = 0.7 — граница), поэтому
  судье *запрещено* ставить `hit = 1` за пустое или общее обоснование.

## 7. `difficulty_anchor`

Ожидаемая доля верных ответов (балл ≥ 0.7) по грейдам: `p_junior ≤ p_middle ≤ p_senior`,
каждое ∈ [0, 1]. Это *априорная* оценка автора; после накопления ответов пул сравнивает
фактический pass-rate с якорем, и отклонение > 20 п. п. — сигнал пересмотреть шаблон
или вариант (§4.2, п. 6). Якорь также используется ярусом A валидации (матрица
грейд × профиль) для синтетических персон.

## 8. `forbidden_changes`, `trap`, `invariant` — как их читает судья

`variant_judge` получает шаблон и сгенерированный вариант и возвращает
`{same_concept, single_correct, difficulty_delta, ambiguity, has_trap, leak_in_statement, reasons}`:

- `same_concept` — вариант проверяет `concept` и сохраняет `invariant`;
- `single_correct` — ровно одна верная опция / одна строка дефекта / однозначный критерий
  полного ответа;
- `has_trap` — ловушка из `trap` присутствует и правдоподобна;
- `leak_in_statement` — условие нарушает `forbidden_changes` (термин-подсказка, вторая верная
  опция, подсказка в комментарии к коду);
- `difficulty_delta`, `ambiguity` — отклонение от эталона.

Вариант принимается при `same_concept ∧ single_correct ∧ |difficulty_delta| ≤ 0.5 ∧
ambiguity ≤ 2 ∧ has_trap ∧ ¬leak_in_statement`. Поэтому все три поля пишутся так, чтобы
их можно было *проверить по тексту варианта*, а не «по духу».

## 9. Статусы: `draft` → `reviewed`

- `draft` — написан автором (человеком или агентом); загружается, виден в
  `GET /assessment/templates`, **в генерацию пула не попадает**.
- `reviewed` — вычитан человеком по чек-листу §10.1 (или агентом-рецензентом §10.2
  с выборочной вычиткой человеком по схеме «если нас двое», PLAN.md §9); рецензент
  заполняет `review: {by, at, notes}`. Только такие шаблоны берёт `python -m app.tools.pool`.
- Правка шаблона со статусом `reviewed` возвращает его в `draft` (меняется смысл —
  варианты, принятые по старому эталону, могут не соответствовать новому); `review.notes`
  хранит, что изменилось.

Эталонные шаблоны 6 октября созданы со `status: draft`: их переводит в `reviewed`
человек, прочитав каждый (≈ 3 минуты на шаблон) — это и есть первая партия вычитки.

## 10. Чек-листы вычитки

### 10.1. Человек (≈ 3 минуты на шаблон)

Форма и файл
- [ ] путь, `id`, `node`, `level` согласованы; `node` есть в `graph.yaml`; загрузчик зелёный
  (`pytest tests/test_templates_load.py`);
- [ ] `kind` соответствует содержимому `anchor_variant` (4 опции / код 15–40 строк / открытый
  ответ);
- [ ] `stack_tags` отражают технологии задания; теги строчными, из общего словаря.

Содержание
- [ ] `concept` — про узел `node` и его уровень; не про соседний узел (N+1 — B3, а не D4;
  индекс — D4, а не B3);
- [ ] уровень по критериям §5: L1 — одно правило; L2 — причина/проект + цена; L3 — скрытая
  несовместимость + план + стоимость;
- [ ] условие самодостаточно: все данные для решения внутри; нет «очевидно», «как известно»;
- [ ] **ровно один** верный ответ (mcq/code_review); для short_design — рубрика покрывает
  всё, что условие требует перечислить;
- [ ] ловушка есть и правдоподобна: неверная опция/решение, которое выбрал бы человек
  с типичным заблуждением;
- [ ] в условии нет подсказки ответа (термин, формулировка, комментарий в коде, имя
  переменной);
- [ ] код `code_review` компилируется «в голове», идиоматичен, без второго дефекта,
  без лишних предупреждений линтера, которые кандидат примет за дефект;
- [ ] `reference_answer` действительно получает полный балл по рубрике и укладывается
  в `max_answer_chars` (для открытых ответов).

Рубрика и калибровка
- [ ] критерии наблюдаемы, не требуют конкретного инструмента там, где есть равноценные;
- [ ] веса отражают важность: первый — концепция; Σ = 1;
- [ ] `difficulty_anchor` и `estimated_minutes` правдоподобны для уровня (§5);
- [ ] `invariant / vary / forbidden_changes` достаточны, чтобы генератор не сломал задание
  (мысленно сгенерируйте вариант в другом домене — остаётся ли один верный ответ?).

Этика и право
- [ ] нет текста ТЗ хакатона, цитат из книги Кичинского, реальных компаний и людей;

### 10.2. Агент-рецензент

Вход: YAML шаблона, этот документ, `graph.yaml` специализации, один эталонный шаблон того же
`kind`. Агент не правит файл — он возвращает вердикт:

```json
{
  "template_id": "be.B3.L2.n_plus_one",
  "verdict": "accept | fix | reject",
  "level_ok": true,
  "single_correct": true,
  "trap_present": true,
  "leak_in_statement": false,
  "rubric_ok": true,
  "issues": [
    {"field": "anchor_variant.code", "severity": "major | minor", "text": "строка 12: второй дефект — утечка сессии"}
  ],
  "suggested_patch": "необязательно: исправленный фрагмент YAML"
}
```

Правила агента: проверять каждый пункт §10.1 и писать `issues` только с указанием поля
и строки; `reject` — при нарушении уровня, неоднозначном ключе или подсказке в условии;
`fix` — при исправимых замечаниях (вес, формулировка критерия, лишний комментарий);
`accept` — без `major`. Человек читает вердикты партиями, выборочно открывает шаблоны
(≈ 20 из 78) и выставляет `status: reviewed` сам: агент статус не меняет.

## 11. Проверки загрузчика (`templates.py`)

Загрузчик читает все `*/templates/*/L*_*.yaml` в `settings.skills_path`, собирает все
проблемы и падает одной `TemplateLoadError` с путями (битый шаблон не выпадает молча):

1. YAML — словарь; неизвестных полей нет.
2. `id` по шаблону `<spec>.<NODE>.L<level>.<slug>`, совпадает с `node`, `level` и путём файла;
   `id` уникален в банке.
3. `node` существует в `graph.yaml` специализации. Если графа ещё нет — предупреждение
   в `catalog.warnings` и лог, проверка пропускается.
4. `level` ∈ 1..3; `kind`, `status` из перечислений.
5. Рубрика: 2–6 критериев, уникальные `id`, Σ `w` = 1.
6. `mcq_reasoned`: ровно 4 опции с ключами A–D, тексты не повторяются, `answer_key` — одна
   буква. `code_review`: `defect_class`, `code` 15–40 строк, `answer_key.line` и
   `accepted_lines` в пределах фрагмента, без `options`. `short_design` /
   `scenario_personal`: без `options` и `answer_key`.
7. `difficulty_anchor` монотонен; `estimated_minutes × 60 ≤ max_time_sec`.
8. `defect_class` только у `code_review`; `stack_tags` строчными, без повторов.

API (день 6): `GET /assessment/templates?spec=&node=&level=&kind=&status=` — роль `admin`;
`GET /assessment/internal/templates` с теми же параметрами — по `X-Internal-Token`.
Ответ `{items: [TemplateMeta], total, warnings}`; `TemplateMeta` — все поля шаблона, кроме
`anchor_variant` (из него отдаётся только `estimated_minutes`), плюс `spec`
и `deterministic_share`. Ошибки формата в банке → 500 `templates_invalid` с `details[{path,
message}]`.
