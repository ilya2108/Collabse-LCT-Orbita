# Интеграция с реестром ФСП и ФСП ID

Реальный API реестра соревнований и ФСП ID командам хакатона не предоставляется: эксперты ФСП
прямо сказали, что ждут от решений имитацию и схему будущей интеграции. Поэтому в этом документе
два слоя. Первый — то, что уже заложено в платформу и работает: модель данных достижений, маппинг
дисциплин в граф навыков, затухание подтверждений, очистка привязки при удалении аккаунта. Второй
— то, что мы предлагаем федерации как контракт обмена и схему входа. Граница между слоями
проведена так, чтобы при появлении настоящего API менялся только адаптер в `app/modules/fsp`,
а не модель данных и не формулы.

## 1. Что даёт интеграция

Верифицированное достижение кандидата из реестра ФСП становится подтверждением узлов графа
навыков — той же единицей данных, что и результат теста, только со своим базовым весом и своей
скоростью устаревания. Победа на профильном событии даёт полный вес, призовое место, финал и
участие — убывающий (1.0 / 0.8 / 0.6 / 0.35); подтверждение усиливает узлы, узлы поднимают
кандидата в выдаче по потребности работодателя. Формулы и сводная таблица — в
[`skills-model.md`](skills-model.md), разделы 3 и 6.

Принципиальное ограничение, согласованное с организаторами: достижения влияют только на
ранжирование внутри категории. Грейд кандидат получает исключительно по результату
адаптивного теста — спортивные успехи дополняют проверку навыков, но не заменяют её. Кандидат
без истории ФСП при этом ничего не теряет: модель аддитивна, штрафа за отсутствие достижений
нет, и карточка честно сообщает, что профиль подтверждён тестом
([`skills-model.md`](skills-model.md) §7). Видимостью кандидат управляет сам — в настройках
приватности профиля есть флаг `show_fsp`, скрывающий достижения из карточки для работодателей.

## 2. ФСП ID как провайдер входа

По словам экспертов ФСП, под капотом ФСП ID работает Keycloak. Наша платформа аутентифицирует
пользователей тоже через Keycloak (собственный realm `fsp`: регистрация, подтверждение почты,
PKCE для SPA), поэтому целевая схема входа «через ФСП ID» — штатный identity brokering: ФСП ID
подключается к нашему realm как внешний OIDC-провайдер, на экране входа появляется ещё одна
кнопка, а в токен попадает claim `fsp_id`, по которому профиль связывается с реестром. Кастомного
кода аутентификации для этого не нужно — это конфигурация Keycloak.

В MVP вход работает через собственный realm, а для связи с реестром в профиле кандидата уже есть
поля `fsp_id` и `fsp_linked_at`. Это даёт запасной путь привязки, не требующий brokering: кандидат
вводит свой ФСП ID и одноразовый код, выданный на стороне реестра, платформа проверяет код и
фиксирует привязку. Сами эндпоинты группы `/fsp` на момент фиксации документации — пустой каркас
роутера (см. [`06-api.md`](06-api.md)); анкета кандидата заполняется вручную, о чём интерфейс
предупреждает явно.

## 3. Согласие на получение данных

Привязка ФСП ID — всегда отдельное явное действие кандидата, а не побочный эффект входа.
Платформа уже умеет фиксировать согласия с версией политики и временем (`POST /auth/consent`,
состояние видно в `GET /auth/me`), и согласие на получение данных из реестра встаёт в тот же ряд:
момент привязки сохраняется в `fsp_linked_at`. Отвязка задумана симметричной — по запросу
кандидата импортированные достижения и подтверждения с источником `fsp` удаляются, и его позиция
в выдаче пересчитывается без них. Полное удаление аккаунта (`DELETE /auth/account`) уже сейчас
стирает `fsp_id` и дату привязки вместе с остальными персональными данными — кандидат не обязан
удалять привязку отдельно.

## 4. Предлагаемый контракт данных о достижениях

Структуру записи о достижении мы предлагаем сами — и она же реализована у нас как таблица
`fsp_achievement`, так что контракт проверен на живой модели данных. Запись состоит из трёх
частей: участник (`fsp_id`), событие (стабильный `event_id`, название, дисциплина, тип и дата
события) и результат (тир `winner | prize | finalist | participant`, занятое место, перцентиль
среди участников, признак командного зачёта). Исходная запись реестра целиком сохраняется в поле
`raw` — туда же ложится ссылка на протокол соревнования; персональных данных в этих записях нет
и быть не должно. Повторная выдача той же записи безопасна: уникальность пары
(кандидат, `event_id`) закреплена ограничением в БД.

```json
{
  "fsp_id": "FSP-2024-018342",
  "event": {
    "event_id": "evt-2025-0411",
    "title": "Чемпионат по спортивному программированию, продуктовая дисциплина",
    "discipline": "продуктовое программирование",
    "event_type": "championship",
    "event_date": "2025-04-11"
  },
  "result": {
    "tier": "prize",
    "rank": 2,
    "percentile": 1.8,
    "is_team": true
  }
}
```

Ответы экспертов ФСП на общей сессии вопросов повлияли на контракт и маппинг напрямую:

| Вопрос | Ответ ФСП | Что изменили у себя |
|---|---|---|
| Доступ к ФСП ID и реестру | Не дадут; ждут мок и схему интеграции; внутри ФСП ID — Keycloak | Схема brokering (§2) и заглушка реестра (§7) вместо попыток живой интеграции |
| Ранжировать ли типы мероприятий | Внутреннего ранжирования нет, чемпионат не «выше» хакатона | В маппинге нет весов по типу события — только тир результата и перцентиль |
| Срок давности достижений | «Можно, но не обязательно» | Ничего: экспоненциальное затухание (§6) и есть срок давности, органичный модели |

## 5. Маппинг дисциплин в узлы

Как текстовое поле «дисциплина» из реестра превращается в конкретные узлы графа, описывает один
файл — `backend/app/skills/fsp_mapping.yaml`. Дисциплина распознаётся по подстрокам
(«олимпиад…», «ctf», «хакатон бэкенд»), а узлы задаются двумя способами: фиксированными
идентификаторами, когда трек однозначен (хакатонный трек «бэкенд» всегда подтверждает be.B1,
be.B2, be.C1, be.C4), или кодами, которые разворачиваются в специализации самого кандидата
(олимпиада по алгоритмам усиливает D2 и D1 той специализации, которой занимается кандидат).
Уровень подтверждения считается либо по перцентилю (топ-10 % участников — уровень 3), либо по
тиру результата; командное событие дополнительно подтверждает узел командной работы C4 с половинным
весом, а участие без результата даёт небольшой вес 0.2 — только за свежесть. Итоговый вес —
произведение веса тира на вес узла, полураспад τ = 365 дней × коэффициент слоя узла.

Новая дисциплина — это новый блок YAML, без изменения кода: при старте backend строго валидирует
файл (несуществующий узел или противоречивое правило уровня не дадут приложению подняться),
а идемпотентный сид переносит маппинг в таблицу `fsp_discipline_map`. Сводная таблица дисциплин
и узлов — [`skills-model.md`](skills-model.md) §6.

## 6. Синхронизация

Импорт достижений задуман как явная синхронизация: она запускается при привязке и затем вручную
(`POST /fsp/sync` в предлагаемом контракте). Идемпотентность заложена на уровне БД — благодаря
уникальности пары (кандидат, `event_id`) повторный запуск не плодит дубликатов и не «освежает»
старые записи. После импорта каждое достижение по маппингу §5 разворачивается в подтверждения
узлов, после чего пересчитывается материализованный снимок силы узлов — тот же, который ночная
джоба `decay-recompute` обновляет для всех кандидатов. Поэтому старение достижений не требует
обращений к реестру: подтверждение теряет вес само, через год остаётся половина, через два —
четверть. Кандидат видит вклад достижений в персональном слое графа
(`GET /candidates/me/skill-states`), работодатель — в карточке кандидата и его позиции в выдаче.

## 7. Заглушка реестра

Раз реального API нет, демонстрация строится на заглушке `fsp-registry-stub` — отдельном небольшом
FastAPI-сервисе, за которым в схеме стенда зарезервирован порт 8020. Его содержимое — участники с
ФСП ID, их достижения в формате контракта §4, одноразовые коды привязки и журнал входящих
запросов, плюс служебная кнопка «добавить достижение»: на демонстрации можно начислить кандидату
победу и показать, как сдвигается его позиция в подборке. Главное архитектурное решение здесь не
заглушка, а адаптер: модуль `app/modules/fsp` общается с реестром через один класс, и замена
заглушки на настоящий стенд ФСП — это замена адреса и реализации адаптера; модель данных, маппинг
и формулы не меняются. На момент фиксации документации сервис-заглушка в compose-стенд ещё не
включён, а группа `/fsp` в API — каркас; статус по пунктам — [`compliance.md`](compliance.md).

## 8. Открытые вопросы и план развития

Без ответа ФСП пока остаются точный состав полей реального реестра и формат протоколов — наш
контракт §4 является предложением, ориентиры по полям (места, перцентили, командный зачёт)
эксперты подтвердили. Открыт и вопрос командных результатов: сейчас командное событие даёт равный
бонус каждому участнику, делить вклад внутри команды реестр не позволяет. Ранжировать типы
мероприятий мы сознательно не стали — это позиция самой федерации.

Дальнейшие шаги поверх уже готовой модели данных: реализовать эндпоинты привязки и синхронизации,
включить заглушку реестра в стенд, настроить identity brokering ФСП ID в Keycloak; за горизонтом
MVP — подписка на события реестра вместо ручного импорта и обратная связь федерации
([`09-beyond-mvp.md`](09-beyond-mvp.md)). Приоритеты и порядок — [`roadmap.md`](roadmap.md).
